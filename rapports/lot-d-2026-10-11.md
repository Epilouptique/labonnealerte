## 2) Connexion Google — à créer chez Google Cloud (à faire par Hugo)
1. **Projet** Google Cloud (ou réutiliser l'existant).
2. **Écran de consentement OAuth** (External) : nom de l'app, e-mail d'assistance, domaine `labonnealerte.fr`, lien vers la politique de confidentialité, scopes minimaux (`openid`, `email`, `profile`).
3. **ID client OAuth 2.0 de type Android** : nom du package de l'app + empreinte SHA-1 du certificat de signature (debug ET release). C'est ce qui permet au téléphone d'obtenir un ID token.
4. **(selon l'intégration) ID client « Web »** : Google Sign-In Android requiert souvent un *serverClientId* de type Web ; c'est cet identifiant-là qui devient l'**audience (`aud`)** du jeton vérifié côté serveur.
5. Me communiquer l'identifiant client à poser en **variable d'environnement Railway `GOOGLE_CLIENT_ID`** (= l'`aud` attendu). **Je n'ai pas modifié de variable Railway.** Tant que `GOOGLE_CLIENT_ID` est absente, la route répond `503` (inactive) — donc inerte en prod.

### Implémenté (serveur)
`POST /api/app/login/google` : vérifie l'ID token auprès de Google (`oauth2.googleapis.com/tokeninfo`, aucune dépendance ajoutée, safe-fetch non touché), contrôle `aud === GOOGLE_CLIENT_ID`, émetteur Google, non-expiration et `email_verified`. Rattache à un compte existant **uniquement** si l'e-mail est vérifié (renseigne `google_id`), sinon crée le compte (acceptation des conditions exigée, comme le flux e-mail). Mêmes limites de débit (`rateOk`/`rateIp`) et mêmes jetons de session (`createSession`).

### Texte proposé pour la confidentialité (NON appliqué)
> **Connexion via Google.** Si vous choisissez de vous connecter avec Google, nous recevons de Google votre adresse e-mail et l'identifiant de votre compte Google, uniquement pour vous identifier et rattacher votre session à votre compte La Bonne Alerte. Nous ne recevons ni votre mot de passe, ni votre liste de contacts. Aucune donnée n'est transmise à Google à des fins publicitaires de notre part.

## 3) PanneauPocket — reconnaissance (aucun code, aucun service tiers contacté)
- **Moteur actuel** : un *poller* (cron ~30 min) interroge chaque source active via un *fetcher* dédié, détecte un changement d'état (activé/désactivé) et appelle `dispatchAlert` → `deliverToSubscribers` (email groupé + push, file de veille). Les événements municipaux (LOT C) réutilisent **le même** `deliverToSubscribers` via `municipal-notify.dispatchDue`, derrière le drapeau global `MUNICIPAL_NOTIFY_ENABLED` (absent/false aujourd'hui, donc inerte).
- **Un formulaire « relier mon PanneauPocket »** exigerait : (a) une **organisation vérifiée** (statut `verified`) rattachée à une commune (INSEE résolu) ; (b) une **URL PanneauPocket validée** côté serveur (format + `safeFetchText` robots-aware, HTTP/flux valides, comme l'aperçu RSS/agenda du LOT 11) ; (c) une correspondance entre la commune déclarée de l'organisation et la page reliée ; (d) un *fetcher* lisant le canal public (RSS/JSON si disponible), **sans** se faire passer pour un compte ni scraper de contenu protégé.
- **Protections à réutiliser du LOT C** : plafond d'envois/jour par organisation, délai d'annulation de 10 min, distinction Alerte/Information (seule l'Alerte notifie), journal des envois, audience = abonnés de la commune (INSEE strict, pas de ciblage quartier), et le drapeau global d'activation. Rien ne doit court-circuiter ces garde-fous.
- **Non fait volontairement** : aucune requête vers PanneauPocket, aucune implémentation — reconnaissance seule.
